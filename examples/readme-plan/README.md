# Example: plan a launch short from this repo's README

A worked example of the `plan` skill (`skills/plan/SKILL.md`), produced by
following the skill by hand with the repository's own `README.md` as the only
source. It is the Phase 2 exit scenario: `/video-studio:plan README.md`
should produce a validated spec and a readable storyboard.

Request used:

```
/video-studio:plan input/README.md
devtool launch short, 30-45 s, vertical, grounding strict
```

## Files

- `project/creative-brief.yaml`: goal `launch`, audience, `youtube_shorts`,
  `9:16`, 40 s, tone, desired action, four scored hook candidates, the
  chosen hook, template `devtool-launch`, and every inferred value in
  `assumptions`.
- `project/video-spec.json`: nine scenes (41 s against a 40 s target), `grounding: "strict"`.

`source/` (the ContentIR) and `project/storyboard.md` are not committed;
they are regenerated by the engine (see below).

## How it follows the skill

- **Hooks**: four candidates with different mechanisms (`contrarian`,
  `promise`, `curiosity_gap`, `question`), scored on relevance, clarity,
  curiosity, evidence strength and visual potential. The contrarian hook
  wins (42/50) and is grounded in the README's "compiles knowledge into
  video" paragraph.
- **Beats**: hook → problem → point → point → proof → demo → context →
  CTA → end card, one idea per scene.
- **Pacing**: every voiced scene sits between 2.3 and 2.7 words per second;
  on-screen text is at most 6 words.
- **Visuals**: all scenes are deterministic `motion_graphic`
  (`typography`, `comparison`, `diagram`, `code`, `cta`, `end_card`), so the
  plan needs no generative spend. No provider or model names anywhere.
- **Grounding**: every scene cites README evidence with the markdown
  extractor's block refs: `markdown:README.md#L3-L6` (intro paragraph),
  `#L12-L15` (what works today), `#L17` (later phases), `#L26-L28` (local
  install command), `#L65` (license).
- **Honesty**: the README says rendering and providers arrive in later
  phases, so the video says so (s07) and the CTA is something that works
  today.

Note: `input/README.md` is a frozen copy of the repo README taken when this
example was planned, so the `claim_refs` line ranges stay valid when the live
README changes. It describes the project at an early phase; the spec says only
what that copy says. To refresh the example, copy the current README into
`input/`, re-ingest, re-plan, and fix the stale refs `spec_validate` reports.

## Reproduce and validate

From the repository root, with the plugin loaded (`claude --plugin-dir .`):

1. Create a scratch project (for example `/tmp/readme-plan`) and copy
   `project/creative-brief.yaml` and `project/video-spec.json` into its
   `project/` folder.
2. Ingest the frozen copy: the `ingest` tool with `project_dir` = the scratch
   project and `inputs` = the absolute path of `input/README.md`. Because
   that file lives outside the scratch project, its refs use the basename:
   `markdown:README.md#L<a>-L<b>`.
3. Run `brief_validate` and `spec_validate` on the scratch project, then
   `storyboard_render` to write `project/storyboard.md`.

`packages/mcp/src/plan.test.ts` runs exactly these steps in CI.
