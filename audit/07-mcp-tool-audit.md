# 07 — MCP tool audit

Server: `engine` v0.1.0, stdio, 28 tools, no resources or prompts (`packages/mcp/src/server.ts:32-33,101-814`).

## Common mechanics

- **Error reporting:** every handler is wrapped in `safe()`. Any throw becomes `{isError: true, content: [{type: "text", text: "error: <message>"}]}` (`server.ts:49-63`). There are no error codes and no `structuredContent` on errors, with two exceptions: `render_submit` spec refusal returns `structuredContent: {ok: false, errors}` (`server.ts:382-388`), and `job_status` for a failed job returns the full view with `isError: true` (`server.ts:422`). Engine errors usually carry a fix in the message (e.g. `TranscribeError` adds `\nFix: …`, `transcribe.ts:57-64`).
- **Output shape:** `jsonResult(summary, data)` returns **three copies** of the result: a text summary, `JSON.stringify(data, null, 2)` as a second text block, and `structuredContent: data` (`server.ts:91-99`). Clients that forward both `content` and `structuredContent` to the model pay for the JSON twice, pretty-printed. This is the single biggest context-cost issue in the server.
- **Input path handling:** `resolveInputPath` only rejects empty or NUL input and resolves relative paths against `process.cwd()`. It does **not** confine anything (`paths.ts:9-13`). Confinement to the project happens only where the engine uses `resolveInsideProject` (realpath, no `..`, no absolute: `core/src/project.ts:181-197`). That covers footage (`pipeline.ts:1162`), transcripts (`pipeline.ts:1220`), sfx (`pipeline.ts:1312`), music files (`music.ts:84`), the brand logo (`pipeline.ts:1945`), and compare's `file` sides (`compare.ts:55-68`).
- **Output schemas:** no tool declares `outputSchema`, although all return `structuredContent`.
- **Trust boundary:** the engine has no process-level sandbox. Any path or URL passed by the model is honoured with the user's permissions. The MCP permission prompt is the only gate.

## Cross-cutting evaluation

| Dimension | Assessment | Evidence |
|---|---|---|
| **Atomicity** | Good at the file level: `writeJsonAtomic`/`writeFileAtomic` everywhere; scene clips rendered to `.tmp` and renamed (`select.ts:282-291`). Weak at the operation level: `qa_run` also exports, `review` also lints, `variants` prepares and renders, `shorts` finds and creates projects. Several tools do 2–3 jobs behind flags, which makes annotations inaccurate | `server.ts:438-445,544-547,620-643,713-723` |
| **Naming** | Short verbs (`test`, `export`, `diff`, `lint`, `review`) are fine inside the `engine` namespace, but `engine` itself is generic and collided with the project-scope copy (`.mcp.json:3`). `project_init` vs implicit creation in `ingest` is redundant | — |
| **Descriptions** | Thorough and fix-oriented. Several run over 1,000 chars and mix contract with coaching (`render_submit` :356, `ingest` :150, `spec_validate` :183, `review` :526). These load into every session's tool list, all 28 of them. Moving advice into the skills would shrink the always-on context | server.ts |
| **Schema clarity** | Mostly good (enums for voice/renderer/quality/mode, ranges on numbers). Gaps: `spec_validate` "exactly one of" not in the schema; `review.mode`, `from_sec`, `to_sec`, `width`, `cols`, `quality_a/b`, `transcribe.project_dir` have no `.describe()`; no cross-field checks (`min_sec < max_sec`, `keep_pause_ms ≤ max_pause_ms`, crop within the frame); no `outputSchema` | server.ts:185-192,530-541,588-589,677,703-704,798-799 |
| **LLM-optimised outputs** | Summaries are good, one line per item. But every result also ships the full pretty JSON twice (text + structuredContent). | **Annotation correctness** | Wrong: `lint` and `verify` `readOnlyHint: true` but they write (`lint.ts:1244-1247`; `verify.ts:286-287`). Understated: `export`, `test(update)`, `variants`, `shorts(make_projects)` and `ingest` delete or overwrite data but say `destructiveHint: false`.
